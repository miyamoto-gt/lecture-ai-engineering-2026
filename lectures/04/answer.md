- 気づき・疑問：
  - 根拠の基準に方針を1行足しただけで、一致率が 7/10 から 9/10 に上がった(+2)。判定のずれは採点モデルの能力ではなく、ルーブリックの曖昧さから来ていた。

  - 「回の表示」のように機械的に決まる基準は、LLM ではなくコードで判定したほうが安定しそうだと思った。宿題で調べた SWE-bench Verified では逆に、コードの判定が正しい解答を落としていたので、基準の性質に合わせて採点者を選ぶ必要がある。


## 宿題

- 取り組んだレベル：発展
- やったこと：
  - SWE-bench Verified(GitHub の issue を直すコーディング課題 500件)を調べた。
    - データセット: https://huggingface.co/datasets/princeton-nlp/SWE-bench_Verified
    - 作成の説明: https://openai.com/index/introducing-swe-bench-verified/
  - Hugging Face の Data Studio で SQL を使って問題を3件開き、issue の本文(problem_statement)、正解の修正(patch)、採点テスト(FAIL_TO_PASS)を読んだ。
    - sympy__sympy-18199: `nthroot_mod`(x^n ≡ a (mod p) を解く関数)が解 x = 0 を返し忘れるバグの修正。issue はシンプルで 0 を返す分岐は思いつくが、正解パッチは長く、法が素数でない場合を解く新しい関数(約45行)が足されていた。issue に対応する修正は2行だけで、残りは issue から想像できない。
    - pylint-dev__pylint-4551: クラス図生成ツール pyreverse が型ヒントを図に表示するようにする機能追加。採点テストが `get_annotation` という関数名を import するが、この名前は issue に書かれていない。別の名前で正しく実装しても不正解になる。
    - django__django-14725: モデルフォームセットで新規作成を禁止し、編集だけ許可する方法の追加。パッチは9行ほどで処理は読めたが、テストが要求する引数名 `edit_only` は issue に書かれていない。
  - OpenAI の記事で作成の人数と手順を確かめた。Python 経験のあるプロの開発者93人が1,699件を検証。事前に50件のテストで検証者を選抜し、1件につき3人が独立に確認する。1人でも問題ありとすれば除外し、68.3%を落として500件にした。採点はテストの実行で、人も LLM も使わない。

- 気づき・疑問：
  - 一番の違いは、正誤を LLM や人ではなく判定処理(テストコード)が決めていること。テストは実行すれば必ず同じ結果になり、LLM 採点のようにぶれない。その代わり、テストに書かれた条件しか見ないので、書いた人の想定から外れた正しい解答を落とす。
  - 実際に読んだ3件とも、不正解の原因はモデルの能力より採点の方にあると感じた。issue に書かれていないこと(追加の機能、関数名、引数名)を判定処理が要求していた。人が採点していれば「名前は違うが機能は正しい」と判断できたはずの解答も、テストは import エラーで不正解にする。
  - ずれ方は2種類あった。sympy はテストが広すぎて頼まれていない機能まで確認する。pylint と django はテストが狭すぎて、正解パッチと同じ名前でないと通らない。
  - 93人が1件につき3人で確認して68.3%を落としても、こうした問題が残っている。人が関わっているのは判定処理が妥当かどうかの事前確認で、採点そのものではない。演習で LLM 採点と人のラベルの一致率を見たのと同じ確認が、コードで判定する基準にも必要だと思った。
  - 疑問: 自分のエージェントの評価セットを作るとき、コードで判定する基準が正しい回答を落としていないかを、1人でどう確かめればよいか。
